# Network Traffic Analysis

## Objective

Inspect network configuration, routing, socket activity, DNS resolution, and captured packets in a Linux environment. The goal is to connect command-line network inspection with packet-level evidence and practice explaining what each observation does—and does not—prove.

## Environment & Tools

- Linux environment using the `eth0` network interface
- `ip` for interface and route inspection
- `ss` for socket and connection inspection
- `ping` for ICMP connectivity tests
- `getent` for hostname resolution checks
- `curl` for generating an HTTPS request
- Wireshark display filtering and `dumpcap` for packet capture

## Methodology & Commands

1. Inspect interface state and addressing with `ip addr show eth0`.
2. Review the routing table and default gateway with `ip route`.
3. Test gateway reachability with `ping -c 4 100.115.92.193`.
4. Inspect TCP and UDP sockets with `ss -tun` and `ss -tn`.
5. Generate an HTTPS request with `curl https://example.com`, then consider whether a point-in-time socket snapshot can capture a short-lived connection.
6. Check name resolution with `getent hosts example.com` and `getent ahostsv4 example.com`.
7. List available packet-capture interfaces with `dumpcap -D`, then capture a limited sample using `sudo dumpcap -i eth0 -c 10`.
8. Generate ICMP traffic with `ping -c 4 8.8.8.8` and isolate it in Wireshark with the display filter `icmp`.

## Key Findings

- The `eth0` interface was UP with IPv4 address `100.115.92.195/28`.
- The directly connected subnet was `100.115.92.192/28`, with default gateway `100.115.92.193`.
- Four ICMP echo requests to the default gateway received replies during the connectivity test.
- The initial `ss` snapshots showed no active connections. After an HTTPS request to `example.com`, the connection had already completed before the next snapshot. This demonstrates how short-lived connections can be missed by point-in-time inspection.
- Hostname resolution for `example.com` returned IPv4 and IPv6 addresses. The IPv4 results observed during the test were `172.66.147.243` and `104.20.23.154`.
- A `dumpcap` capture on `eth0` collected 10 packets with 0 dropped packets.
- Wireshark's `icmp` display filter showed ICMP Echo Request and Echo Reply packets generated by the ping test.

These observations describe the test environment and capture period only; they do not establish that the network was free of other activity or security issues.

## Remediation / Security Takeaway

- Confirm which interfaces, addresses, and routes are expected for the host before treating them as suspicious.
- Identify the process associated with unexpected listening ports or connections rather than guessing from a port number alone.
- Remember that socket listings are snapshots; use packet capture or continuous monitoring when investigating brief connections.
- Correlate DNS lookups, destination addresses, process activity, and packet timestamps when investigating unexpected outbound traffic.
- Use narrow capture filters and bounded capture sizes to keep investigations focused and manageable.
- Treat successful ping or DNS results as limited observations, not proof that all services or paths are healthy.
